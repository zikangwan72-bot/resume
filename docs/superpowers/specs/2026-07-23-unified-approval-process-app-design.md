# 统一流程应用与低代码审批中心设计规格

> 版本：v1.0  
> 日期：2026-07-23  
> 状态：已完成产品讨论，待用户审阅书面规格

## 1. 背景与目标

当前审批后台把“审批类型、表单模板、流程模板”拆成三套配置和三个页面。管理员必须先分别创建配置，再手工关联，操作路径复杂，且不利于后续增加条件分支、版本管理、流程监控和 AI 审批能力。

本次改造将三套概念统一为“流程应用”。管理员在一个编辑器中完成基本信息、表单设计、流程设计和发布。员工仍通过审批中心发起和处理申请。

本期目标：

- 将审批类型、表单模板和流程模板合并为统一流程应用。
- 提供组件式低代码表单设计器。
- 支持串行审批、会签和简单条件分支。
- 审批节点可以自由选择任意启用员工，不依赖上下级组织关系。
- 用户新增时职位必填，申请表自动带入姓名、部门、职位和申请时间。
- 提供只读流程监控报表和实例详情。
- 支持草稿、发布、停用和不可变版本。
- 保留请假、报销和采购三个示例，并迁移为流程应用。

本期不做：

- 页面权限、功能权限和数据权限的进一步拆分。
- 完整组织架构树或直属上下级关系。
- BPMN、任意循环、复杂并行网关和动态子流程。
- 管理员催办、转交、强制通过或终止运行中的流程。
- AI、RAG、Copilot 或 Agent 功能。

## 2. 方案选择

采用“统一流程应用模型”，而不是仅在前端包装旧三表，也不引入完整 BPMN 引擎。

每个流程应用包含：

- 基本信息
- 表单定义
- 流程图定义
- 草稿与发布状态
- 版本记录

已发布版本不可修改。编辑已发布流程时创建下一草稿版本；发布后，新申请使用新版本，旧申请继续运行提交时保存的快照。

## 3. 信息架构

### 3.1 管理员页面

| 页面 | 建议路由 | 作用 |
|---|---|---|
| 用户管理 | `/admin/users` | 新增、编辑、启停员工并维护部门、职位和角色 |
| 流程应用 | `/admin/process-apps` | 查看、创建、复制、编辑、发布和停用流程应用 |
| 流程应用编辑器 | `/admin/process-apps/new`、`/admin/process-apps/:id/edit` | 完成四步式低代码配置 |
| 流程监控 | `/admin/process-monitor` | 查看统计、筛选实例和打开实例时间线 |

原“审批类型、表单模板、流程模板、审批日志、角色管理”入口移除。角色字段合并进用户管理，审批日志合并进流程监控详情。

本期沿用现有 `approval:manage` 路由保护，不新增权限模型。

### 3.2 员工页面

保留以下页面和主要行为：

- 审批中心
- 发起申请
- 我的申请
- 待我审批
- 我已审批
- 审批详情

员工发起申请时只看到状态为“已发布”的流程应用。

## 4. 用户管理

用户字段：

| 字段 | 规则 |
|---|---|
| 姓名 | 必填 |
| 邮箱 | 必填且唯一 |
| 部门 | 必填 |
| 职位 | 必填 |
| 角色 | 必填，仅作为当前业务身份标签 |
| 状态 | 启用或停用 |

本期不维护直属上级和部门负责人。流程创建者可以在审批节点中从全部启用员工中自由选择审批人。

停用规则：

- 停用员工不能用于新流程配置。
- 已发布流程引用停用员工时，禁止产生新申请并提示管理员修复流程。
- 已经运行的申请继续使用提交时保存的审批人快照。

## 5. 流程应用生命周期

流程应用状态：

- `draft`：草稿，可以编辑和预览，员工不可发起。
- `published`：已发布，员工可以发起。
- `inactive`：已停用，禁止新申请，历史记录仍可查看。

版本规则：

1. 新建流程时创建草稿版本。
2. 首次发布生成 `v1`。
3. 编辑已发布流程时复制出下一草稿版本。
4. 发布下一草稿版本后，新申请使用新版本。
5. 已发布版本不可覆盖或删除。
6. 运行实例始终使用提交时保存的表单、流程和申请人快照。

流程应用列表展示名称、分类、字段数、节点数、当前版本、状态、更新时间以及预览、编辑、复制和停用操作。

## 6. 四步式流程应用编辑器

### 6.1 第一步：基本信息

字段包括名称、唯一编号、分类和说明。唯一编号发布后不可修改。

### 6.2 第二步：表单设计

采用三栏布局：

- 左侧为字段组件库。
- 中间为表单实时预览和排序区域。
- 右侧为当前字段属性。

支持的组件：

- 单行文本、多行文本
- 数字、金额
- 日期、日期范围
- 单选、多选、下拉选择
- 人员选择、部门选择
- 附件上传
- 分组标题
- 明细表格

支持添加、删除、复制和上下排序。字段属性包括名称、字段键、提示文字、是否必填、默认值和选择项。

每个流程自动包含不可删除的“申请人信息”分组：

- 申请人姓名
- 所属部门
- 职位
- 申请时间

这些字段只读，并在提交时保存快照。

明细表格允许配置列，列类型限于单行文本、数字、金额、日期和下拉选择。第一版不支持明细表格嵌套。

### 6.3 第三步：流程设计

画布固定包含开始和结束节点。管理员可以添加：

- 单人审批节点
- 会签节点
- 条件分支节点

单人审批节点选择一名启用员工。会签节点至少选择两名启用员工，所有人同意后才能继续；任一人驳回则申请驳回。

条件分支使用结构化配置，不允许输入代码。条件格式为“字段 + 运算符 + 比较值”。支持：

- 等于、不等于
- 大于、大于等于
- 小于、小于等于
- 包含、不包含

条件可以引用数字、金额、单选、下拉和文本字段。每个条件节点至少包含一条条件分支和一条默认分支。分支按显示顺序匹配，第一条命中的分支生效；没有命中时进入默认分支。

第一版流程图必须是有向无环图，不支持回路。所有分支必须最终到达结束节点。

节点公共属性包括节点名称和超时时间。审批节点额外包含审批人、是否允许转审；会签节点包含多个审批人。

### 6.4 第四步：预览与发布

管理员可以同时预览员工表单和流程走向，并选择保存草稿或发布。

发布前必须校验：

- 至少存在一个业务字段。
- 至少存在一个审批节点。
- 每个审批节点已选择有效审批人。
- 会签节点至少有两名审批人。
- 条件引用的字段存在且类型可比较。
- 每个条件节点存在默认分支。
- 节点和连线不存在断点或环路。
- 从开始节点出发的所有路径都能到达结束节点。
- 流程引用的员工均为启用状态。

校验失败时，页面按编辑步骤分组展示中文错误，并允许点击错误跳转到对应字段或节点。

## 7. 运行时数据流

员工提交申请时：

1. 后端读取当前已发布版本。
2. 校验表单字段、必填项和审批人状态。
3. 根据完整表单数据计算条件分支。
4. 将选中的执行路径解析为顺序审批节点。
5. 保存流程版本、表单定义、选中路径和申请人信息快照。
6. 创建审批实例和第一个待处理节点。
7. 后续节点在前一节点完成后进入待处理状态。

条件只引用提交时已知的表单字段，因此分支在提交时一次性确定，运行中不重新计算。

重复提交通过请求幂等键避免生成两个实例。已完成或已驳回节点不能再次处理。

## 8. 数据模型

### 8.1 流程应用

`process_apps`：

- `id`
- `code`
- `name`
- `category`
- `description`
- `status`
- `current_version_id`
- `created_at`
- `updated_at`

### 8.2 流程版本

`process_versions`：

- `id`
- `process_app_id`
- `version_number`
- `status`
- `form_schema` JSON
- `flow_schema` JSON
- `published_at`
- `created_at`

`form_schema` 使用稳定字段 ID。`flow_schema` 使用稳定节点 ID，并分别保存节点列表和连线列表。条件引用字段 ID，不引用容易变化的显示名称。

### 8.3 用户

现有 `approval_users` 增加必填 `position` 字段。部门继续使用当前文本字段，本期不新建部门树。

### 8.4 审批实例

`approval_requests` 调整为引用流程应用和版本，并增加：

- `process_app_id`
- `process_version_id`
- `applicant_snapshot` JSON
- `form_schema_snapshot` JSON
- `flow_snapshot` JSON
- `idempotency_key`

现有表单数据、状态、当前节点和时间字段继续保留。

`approval_nodes` 增加稳定 `node_key` 和节点超时时间。`approval_actions` 继续保存所有审批行为。

## 9. 流程监控

流程监控只读。

顶部指标：

- 流程总数
- 审批中
- 已通过
- 已驳回
- 已撤回
- 已超时

筛选项：

- 流程应用
- 运行状态
- 提交时间范围
- 申请部门
- 申请人
- 当前审批人
- 是否超时

明细列：

- 流程编号
- 流程名称与版本
- 申请人、部门和职位
- 提交时间
- 当前节点和当前审批人
- 已运行时间
- 状态
- 是否超时

节点超过配置的 `timeout_hours` 且仍为待处理时，实例标记为超时。未配置处理时限的节点不参与超时统计。

实例详情展示表单快照、版本、流程路径、节点时间线、审批意见和操作日志，不提供流程干预按钮。

## 10. 旧数据迁移

当前正式 `approval.db` 中没有审批申请、审批节点和审批操作记录，只有请假、报销和采购三套示例配置。

实施时执行一次受控迁移：

1. 复制备份现有 `approval.db`。
2. 建立新版表结构。
3. 将请假、报销、采购转换为三个流程应用及其 `v1`。
4. 验证三个流程的字段、审批人和节点数量。
5. 确认新版功能正常后，旧配置表不再被代码引用。

迁移不能在普通应用启动时自动删除数据库。迁移失败时保留备份并停止，不启动部分完成的新版数据。

## 11. 错误处理

- 保存失败时保留前端编辑状态，并显示可重试提示。
- 发布校验失败时不创建版本。
- 流程引用停用员工时阻止发布或提交。
- 条件引用已删除字段时立即标记流程无效。
- API 返回统一中文业务错误和稳定错误码。
- 审批动作使用事务，节点状态和操作日志必须同时成功或同时回滚。
- 重复审批返回“该节点已处理”，不重复写日志。
- 列表和监控接口使用分页，避免一次加载全部实例。

## 12. 测试与验收

### 12.1 后端测试

- 流程应用草稿、发布、停用和版本不可变。
- 表单定义与流程图发布校验。
- 用户职位必填和邮箱唯一。
- 任意员工可被选择为审批人。
- 串行审批正确推进。
- 会签必须全部同意，任一驳回后不再推进。
- 不同金额进入不同条件分支。
- 停用员工阻止新申请但不影响已有快照。
- 幂等提交不会创建重复实例。
- 监控筛选和超时统计准确。

### 12.2 前端测试

- 用户新增表单强制填写职位。
- 字段添加、复制、删除、排序和属性修改。
- 单人、会签和条件节点配置。
- 发布错误可以定位到对应字段或节点。
- 发起页面自动展示申请人信息。
- 流程监控筛选与详情跳转。
- 桌面和窄屏布局不发生遮挡或溢出。

### 12.3 端到端验收场景

1. 管理员新增一名带职位的员工。
2. 管理员创建包含金额和附件字段的流程应用。
3. 配置普通金额分支和高额分支，并分别选择审批人。
4. 预览并发布 `v1`。
5. 员工提交普通金额申请，系统自动带入申请人信息并进入普通分支。
6. 员工提交高额申请，系统进入高额分支和会签节点。
7. 审批人完成单人审批与会签。
8. 管理员在监控页按流程、状态和提交时间筛选，并查看时间线。
9. 管理员编辑流程并发布 `v2`，验证旧实例仍显示 `v1` 快照。
10. 停用流程后无法再发起，但历史实例仍可查看。

## 13. 后续 AI 扩展点

本期不实现 AI，但统一流程应用为后续预留以下位置：

- 提交前制度 RAG 与材料完整性检查。
- 审批 Copilot 的摘要、风险提示和意见草稿。
- AI 节点的人工确认、失败回退和运行日志。
- 监控报表的流程瓶颈解释与优化建议。

AI 不直接替代高风险审批决定，任何自动建议都必须保留人工确认和审计记录。
